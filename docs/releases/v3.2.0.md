## 1. AI Provider Readiness Status (Faz 3.2.0B)

**Commit:** `2e60c7a16314e1465d51817aab249ad3fc2cfcfd`
(`feat(ai): add provider readiness status UI`)

### Backend — `GET /api/ai/providers`

The existing authenticated endpoint is extended with a new
`readiness_status` field per provider (backward-compatible: no existing
field removed or renamed):

```json
{
  "providers": [
    {
      "name": "...",
      "model_identifier": "...",
      "available": true,
      "readiness_status": "model_ready"
    }
  ]
}
```

**Response field contract:**

| Field              | Always present | Contains secrets? |
|--------------------|---------------|-------------------|
| `name`             | yes           | no                |
| `model_identifier` | yes           | no                |
| `available`        | yes           | no                |
| `readiness_status` | yes (v3.2.0+) | no                |

Sensitive provider configuration — `api_key`, `base_url`, `timeout`,
`keep_alive` — is **never** returned. The `readiness_status` value is a
safe human-readable string; it contains no URL, port, key, or
configuration detail.

**Ollama readiness probe:**

A dedicated `GET /api/tags` probe is used to determine Ollama's live
readiness state.  The probe timeout is `_OLLAMA_PROBE_TIMEOUT_SECONDS =
5 s`, deliberately separate from the 120-second per-request inference
timeout.  Possible values of `readiness_status` for Ollama:

| Value                | Meaning                                         |
|----------------------|-------------------------------------------------|
| `model_ready`        | Server reachable, configured model is loaded    |
| `model_missing`      | Server reachable, model not yet pulled          |
| `server_reachable`   | Server reachable, model list unreadable         |
| `server_unavailable` | Server not reachable within the probe timeout   |

For `DeterministicModelClient`: `not_applicable` (always available,
readiness concept does not apply).  For other providers: `enabled` or
`disabled` based on env-config, no network call.

The probe is **fail-closed**: any error path returns a safe status string
and never raises or leaks internal details.

### Frontend — Assembly Intelligence Page

A new **AI Provider Status** card is added to the Assembly Intelligence
page (`#page-assemblyintelligence`):

- loads once when the page is opened (`showPage` dispatch hook)
- **manual refresh** only — no background polling
- pill-coded status: `pill-ok` (ready/enabled), `pill-warn`
  (reachable/missing), `pill-nok` (unavailable), `pill-info`
  (not_applicable/disabled/unknown)
- all provider name and model values are HTML-escaped (`aiEsc()`) before
  rendering — no injection vector

The `aiAssessAssembly()` function and `POST /api/assembly-intelligence/assess`
flow are **unchanged**.

## 2. Unknown Provider Status Normalization (Faz 3.2.0C)

**Commit:** `07c8ab4e06622337a93a7664088035e0d88ac0a8`
(`fix(ai): localize unknown provider status`)

Any `readiness_status` value not in the known allowlist is normalized to
`"unknown"` before i18n key lookup:

```
Allowlist: not_applicable · enabled · disabled ·
           server_unavailable · server_reachable ·
           model_missing · model_ready · unknown
```

A future backend value that is not in this list will:

- display as **? Unknown** (EN) / **? Bilinmiyor** (TR)
- use the existing `ai.provider.status_unknown` i18n key
- render with `pill-info`
- produce **no** missing-i18n console warning

This makes the UI forward-compatible with new provider states without
requiring a frontend change.
